# AI 原生游戏设计理念

Last updated: 2026-07-15

本文说明 Compiler 的产品理念，以及比赛版本已经实现和后续规划之间的边界。它不是字段级规范；具体 ABI、Schema、白名单、校验器和激活行为仍以 `shared/schemas/`、`tools/`、`docs/AI_COMPILATION_SYSTEM_V0_1.md` 及对应专题文档为准。

## 1. 核心主张

AI 不应只作为开发者制作游戏时使用的提效工具，也应原生成为玩家可感知、可操作、可承担后果的玩法机制。

Compiler 借鉴 Vibe Coding 的交互范式：玩家不需要先学习游戏内部 API，也不需要手写脚本，而是用自然语言表达“我想解决什么问题、想创造什么东西”。系统再把玩家意图、当前游玩状态和创造力编译成受控、可验证、可执行的游戏内容。

```text
玩家自然语言意图
  + 当前世界、节点、敌情、材料和历史状态
  + 开发者定义的能力与安全边界
  -> AI 生成结构化候选
  -> Schema / 白名单 / 预算 / 模拟 / 晋升 / 激活门
  -> 当前 Session 内可执行、可审计、可回滚的游戏内容
```

因此，Compiler 的重点不是“AI 写了一段像游戏的文字”，而是玩家的想法是否真的改变了下一次部署、攻击、控制、资源使用和战斗结果。

## 2. 从生成内容到编译内容

“生成”只回答内容是否被创造出来；“编译”还必须回答它能否进入游戏。

一个可进入 Compiler 运行时的结果至少需要满足：

- **有明确输入上下文**：玩家意图与当前世界状态共同参与，不把提示词当成孤立命令。
- **有稳定目标协议**：候选必须降低到运行时认识的 Capability ABI，而不是输出任意代码。
- **有结构与语义约束**：Schema、枚举和白名单限制对象形态、引用和可执行效果。
- **有玩法预算**：伤害、范围、冷却、费用、目标数、生命周期以及 Provider 延迟和调用成本都有边界。
- **有可重复验证**：确定性模拟和评分检查候选能否部署、触发、结算，以及实际行为是否对应描述。
- **有显式发布权限**：晋升不等于生效；只有通过 Session 激活门的包才能改变当前玩家的运行时。
- **有失败路径**：Provider、媒体或审查失败时，使用 reviewed fallback，并保留拒绝、回滚和审计证据。

AI 在这里负责扩大候选空间，运行时权威仍属于可验证的游戏内核。

## 3. 开发者提供可控内核

AI 原生玩法并不意味着把游戏规则交给模型。开发者不必预写每一个最终对象，但必须定义模型可以组合的能力边界。

这个可控内核包括：

| 内核部分 | 作用 |
| --- | --- |
| Capability ABI | 规定运行时真正能够执行哪些放置、攻击、触发、控制和支援行为 |
| Schema 与白名单 | 规定对象结构、引用关系、合法效果和允许修改的状态范围 |
| 预算 | 限制数值强度、内容规模、延迟、重试次数和 Provider 成本 |
| 上下文装配 | 只向编译任务提供当前需要、允许暴露且可追溯的世界事实 |
| 模拟与评分 | 在激活前验证玩法行为、数值边界和描述一致性 |
| 晋升与激活门 | 区分候选、已审查包和当前 Session 真正生效的内容 |
| Fallback 与回滚 | 保证生成失败不阻断游玩，错误激活可以被审计和撤回 |

开发者设计的核心不只是固定内容列表，而是一组“什么可以被创造、怎样证明它可玩、谁有权让它生效”的规则。

## 4. 三方权限

- **玩家提供意图**：描述目标、偏好和创意，不直接取得代码执行或世界状态写入权限。
- **AI 提供候选**：结合上下文提出结构化方案，但无权自行声明方案有效、写入世界或激活运行时。
- **受控内核作出裁决**：校验器、模拟器、预算、晋升报告和激活门共同决定候选能否被当前 Session 使用。

这使开放式表达和确定性运行可以同时存在：输入可以自由，执行必须有界。

## 5. 比赛版本已实现

以下能力已经进入比赛版本，不是远期概念：

| 能力 | 当前实现 |
| --- | --- |
| 自然语言研发提案 | 玩家可在世界内工坊表达构想，系统结合世界、材料、敌情和玩法约束生成结构化候选 |
| 塔、陷阱、支援道具闭环 | 三类对象已经走通生成、校验、确定性模拟、评分、晋升、激活和前端实际行为 |
| 真实 Provider 与降级 | 已接真实文本 / 媒体 Provider；支持多 Provider fallback，并在调用或门禁失败时回退到 reviewed / deterministic 内容 |
| Session 激活 | 编译产物通过显式激活进入当前匿名 Session，保留隔离、回执和回滚边界 |
| 三种编译世界 | 仙侠、西幻、科幻三个世界实例由真实 Provider 生成，并可进入档案、世界配置、开场、战略地图、节点 / 工坊、首战与结算页面链路 |
| 地图编译 | 地图逻辑结构、运行包和分层表现编译已经接通；玩家默认使用经过审查的表现包或 reviewed fallback，不从生成图片反推路线、塔位和碰撞 |

比赛版本中的“真实闭环”主要指玩家研发的塔、陷阱和支援道具。三种扩展世界与地图属于开发期真实编译后进入页面运行包，不代表玩家游玩时每一步都实时重新生成。

《长夜灯火》的剧情、任务、事件和战后状态变化目前主要由已审查内容、确定性状态投影和受控 delta 支撑。现有 Schema、审查包或调度证据证明了边界存在，但不应被表述为这些系统已经全部由 AI 实时驱动。

## 6. 后续规划

下一阶段会把同一套意图编译范式更深地接入：

- **剧情**：根据玩家行为与已提交世界事实编译可验证的剧情推进，而不是自由续写。
- **任务**：让任务条件、目标、奖励和失败后果成为可模拟、可提交的玩法对象。
- **随机事件**：在概率、频率、资源影响和世界一致性预算内生成事件候选。
- **科技树**：把玩家长期偏好和已验证样品编译成受约束的研究分支与解锁关系。
- **长期世界演化**：让跨战斗的区域、角色、资源和冲突持续变化，并始终通过事务、语义门和回滚策略提交。

这些方向已有部分 Schema、确定性样例和审查证据，但更深的实时 Provider 接入、玩家侧动态消费和长期平衡仍属于规划，不能作为比赛版本已完成能力宣传。

## 7. 设计判断标准

一个功能是否真正“AI 原生”，可以用以下问题检查：

1. 玩家是否通过表达意图参与了内容创造，而不只是观看 AI 生成文本？
2. 生成结果是否成为可部署、可触发、可结算或可提交的玩法对象？
3. 结果是否结合当前 Session 的世界和游玩状态？
4. 模型是否只能调用开发者授权的能力，而不能执行任意代码或直接修改事实？
5. 结果是否经过结构校验、预算、模拟和激活门，并能在失败时安全降级？
6. 玩家创造的内容是否会产生可理解、可追踪的游戏后果？

只有同时回答了“能创造什么”和“为什么允许它运行”，AI 才真正从开发工具进入玩法本身。
